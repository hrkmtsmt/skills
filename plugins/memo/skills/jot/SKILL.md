# jot

作業中に「忘れないうちに」と出てきたことを、流れを止めずに預かるスキル。
ユーザーにとって価値があるのは「今の集中を切らさずに、思い出したことを失わないこと」。だから記録は最短で済ませ、メモの中身には踏み込まない。議論や実装を始めたり、余計な出力をコンテキストに積んだりすると、ユーザーが守りたかった本題の流れを自分で壊すことになる。

預かるのは、ユーザーがあとから見返すための書き置き（アイデア、TODO、確認事項、気づきなど）。「今後はコミットを日本語にして」のように Claude の振る舞いを変えたい依頼は、Claude のメモリ（CLAUDE.md や memory）に入れるものなので、ここには書かない。

## 書き留める

1. 本文を決める。ユーザーの言葉をそのまま使う。言い換え・要約・清書はしない。
   ただし「これ」「ここ」「さっきの」のように会話の文脈がないと後で読めない語があれば、末尾に `（文脈: ○○）` として最小限の補足を足す。数週間後に別のプロジェクトで一覧を見ても意味が通る、が基準。
2. 1回の Bash で追記する。本文は heredoc で標準入力に渡す（引用符や記号をシェルに解釈させないため）。

   ```bash
   python3 ${CLAUDE_SKILL_DIR}/scripts/jot.py add --session "${CLAUDE_SESSION_ID}" <<'JOT'
   本文
   JOT
   ```

   出力の `#番号` がそのメモのIDになる。プロジェクト名は git のルート（なければカレントディレクトリ）の名前が自動で付く。
3. 返答は1行だけ: `📝 #12 メモした`。メモへの感想・評価・質問・提案はしない。
4. 元の作業に戻る。
   - 同じメッセージに本題の指示もあれば、メモの後にそのまま本題を処理する。
   - 作業の途中に割り込んできたメモなら、中断した地点から続ける。「どこまでやったか」の説明もいらない。
   - メッセージがメモだけで、進行中の作業もなければ、1行の返答で終える。

メモの中身を実行しない。「あとで認証まわりをリファクタしたい」「明日 CHANGELOG を更新する」と書かれても、今は手を付けない。ユーザーが「あとで」と言った判断を尊重する。
1つのメッセージに複数のメモがあれば、それぞれを別のメモにする（`add` を続けて呼ぶ）。

## それ以外のとき

次の場面では、[references/manage.md](references/manage.md) を読んでから対応する。書き留めるだけのときは読まなくてよい。

- メモの一覧を見たい、済み・見送りにしたい、Markdown に書き出したいと言われたとき。
- ユーザーが「ありがとう、今日はここまで」「終わり」「おつかれ」「また明日」のように会話を締めくくったとき。このセッションでメモを書き留めていれば、締めくくりの返事の最後に未着手のメモを振り返る。

自分のタスク完了報告は締めくくりに含めない。メモを書き留めたのと同じターンでも振り返らない。「📝 メモした」の直後にメモを並べると、本題から注意をそらしてしまう。
